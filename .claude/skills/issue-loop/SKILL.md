# 이슈 처리 루프

Issue 하나를 받아 **기계 구간이 할 수 있는 데까지 전부 밀고**, 사람이 승인 · 반려를 판단할 수 있는
자리에 정확히 세워 두고 끝난다. 사람 대신 판단하지 않는 것이 이 스킬의 값어치다.

```
Issue 확정 → 계약 확인 → 세션 복구 → 브랜치
  → [시도] 테스트·구현 → npm run verify → 시도 코멘트   ← 실패하면 상한까지 반복
  → 커밋 · 푸시 · PR → CI 폴링(re-run 1회) → LLM 리뷰 코멘트
  → 「사람 차례」 코멘트 → 멈춤
```

**규칙의 원본은 `docs/harness/`다.** 이 문서와 다르면 그쪽이 맞다.
헷갈리면 `03-loop.md`(시도 · 기록) · `04-decision.md`(사람 · 리뷰) · `01-ssot.md` §0(소유권)의 해당 절만 읽는다.

**한 번 호출 = Issue 하나.** 여러 이슈를 동시에 잡지 않는다 — 시도 번호가 겹친다 (03 §6).

## 0. 시작 전 확인

```bash
gh auth status                    # 인증 안 되면 여기서 멈추고 사람에게 알린다
git status --short                # 작업 트리가 더러우면 사람에게 물어본다 (남의 작업일 수 있다)
git fetch origin && git log --oneline -1 origin/main
```

작업 트리에 손대지 않은 변경이 남아 있으면 **치우지 말고 물어본다.** 기록에 없는 시도의 흔적일 수 있고,
그건 DEC-1 ⑤(기록과 실제 상태가 어긋남)에 해당한다.

## 1. 대상 Issue 확정

번호를 들었으면 그 번호다. 못 들었으면:

```bash
gh issue list --state open
```

열린 이슈가 하나면 그것으로 진행하되 **무엇을 잡았는지 먼저 한 줄 말한다.**
여럿이면 목록을 보여주고 고르게 한다 — 엉뚱한 이슈에 브랜치와 PR을 만드는 비용이 크다.
열린 이슈가 없으면 그 사실을 알리고 끝낸다.

## 2. Issue 읽기 — 계약 확인

```bash
gh issue view <N>                 # 본문: 6개 항목
```

Issue는 **그 작업의 SSOT**다 (SSOT §0 Issue 절). 대화 · 계획 문서 · HANDOVER에 다른 말이 있어도 Issue를 따른다.
본문에서 이 여섯 개를 뽑아 적어 둔다. 앞으로의 모든 판단이 여기서 나온다.

| 항목 | 쓰임 |
|---|---|
| 1 배경 | 왜 하는가 |
| 2 변경할 내용 | 손댈 파일 · 모듈의 범위 |
| 3 종료 조건 | C1 · C2 … 와 `(수동)` 표시 |
| 4-1 테스트 기능명 | 브랜치 이름과 테스트 파일 이름이 여기서 나온다 |
| 4-2 기계 검증 | 조건 ↔ `it()` 매핑 |
| 5 건드리면 안 되는 것 | 보호 영역 (기본 + 이 작업 추가분) |
| 6 최대 횟수 | 시도 상한 M |

**6개 항목이 비었거나 종료 조건을 참 · 거짓으로 판정할 수 없으면 추측으로 채우지 않는다** (DEC-1 ③).
`중단(NEEDS_HUMAN)` 코멘트를 달고 멈춘다 — 이것도 시도 1회다 (LOOP-6).

## 3. 세션 복구 — 지금 누구 차례이고 몇 회차인가

```bash
gh issue view <N> --comments      # 뒤에서부터 읽는다
```

**시도 횟수의 원본은 Issue 코멘트뿐이다** (LOOP-4). 대화 기억 · 작업 트리 · PR은 원본이 아니다.
`사람 판단 · 판단 확정` 코멘트가 있으면 **그 뒤의 시도만** 센다 (LOOP-7). 코멘트가 없으면 0회.

마지막 코멘트로 턴을 판정한다 (03 §4 표).

| 마지막 코멘트 | 턴 | 다음 |
|---|---|---|
| 없음 · `시도 N/M · 실패` · `복귀` · `사람 판단 · 반려` | AI | 남은 시도 확인 후 §5 |
| `사람 판단 · 판단 확정` | AI | 시도 0/M 으로 초기화하고 §5 |
| `시도 N/M · 통과` | AI | 이미 통과했으면 §7(커밋 · PR)부터 |
| `사람 차례` · `사람 판단 · 승인` · `사람 판단 · 요구사항 변경` · `중단(…)` · `종료(…)` | **사람** | **손대지 않는다** |

턴이 사람이면 무엇을 기다리는 중인지 한 줄로 보고하고 끝낸다. 기다리는 중에 코드를 고치면
사람은 자기가 본 것과 다른 것을 승인하게 된다.

남은 시도 = M − N. **0이면 새 시도를 시작하지 않고** `중단(상한 소진)`으로 사람에게 넘긴다 (LOOP-3).

이어서 할 때 `npm run verify`를 **먼저 돌려보지 않는다.** 그 자체로 한 시도를 쓴다 (LOOP-1).

## 4. 브랜치

`main`에서 딴다. 이름은 Issue 4-1의 기능명을 쓴다.

```bash
git checkout main && git pull --ff-only
git checkout -b feat/issue-<N>-<기능명>      # 이미 있으면 checkout 만
```

이어받는 작업이면 그 브랜치가 이미 있다 — 새로 만들지 말고 그 위에서 계속한다.
문서만 고치는 이슈면 `docs/…`로 접두사를 바꾼다.

## 5. 기계 구간 — 한 시도

**시도 1회 = 구현부터 `npm run verify` 실행까지다** (LOOP-1). verify 이전의 수정은 —
타입 오류 정정이든 린트든 몇 번을 고치든 — 전부 같은 시도 안이다. 한 번 돌리면 결과와 무관하게 그 시도는 끝난다.

순서가 중요하다. 테스트를 먼저 쓴다.

1. **종료 조건 → 테스트**
   `tests/issues/issue-<N>-<기능명>.test.ts` 에 자동 검증 조건마다 `it('C1. …')` 하나.
   `(수동)`이 붙은 조건은 테스트하지 않는다 — 사람이 화면에서 본다.
   숫자 · 날짜는 종료 조건이 아니라 **테스트가 고른다.** 경계(같을 때 · 하나 넘을 때 · 오늘 당일)를 넣고
   날짜는 `today()` · `addDays()`로 상대 계산한다. 기존 테스트(`tests/helpers.ts`)의 방식을 따른다.
   **시드 데이터를 건드리지 않는다.** 전용 상품 · 전용 로트를 만들고 끝나면 지운다 —
   시드를 소비하면 `stock-invariant.test.ts`의 불변식과 충돌한다 (실제로 Issue #3 시도 1이 여기서 실패했다).

2. **변경 전 코드에서 실패하는 것을 확인** (Issue 4-2의 체크 항목)
   ```bash
   git stash push -- src/            # 테스트만 남기고 구현을 치운다
   npx vitest run tests/issues/issue-<N>-<기능명>.test.ts
   git stash pop
   ```
   실패하지 않는 테스트는 아무것도 지키지 못한다. 어느 조건이 어떻게 실패했는지 코멘트에 적는다.

3. **구현**
   Issue 2번의 범위 안에서만 고친다. **Issue에 없는 변경은 하지 않는다** — 필요하다고 판단하면
   직접 넓히지 말고 새 Issue를 제안한다 (SSOT §0). 범위를 넘지 않았지만 스스로 정한 설계 판단이 있으면
   그건 해도 되고, 대신 코멘트의 `사람 판단이 필요한 것` 칸에 **전부 적는다** (DEC-3).
   아키텍처 규칙 B1~B6(`'use server'`는 `src/actions/`만 · Server Action마다 `requireUser()` ·
   클라이언트 모듈은 db를 값으로 import 금지 · API 라우트 없음 · 상태관리 라이브러리 없음)을 어기면 `npm run arch`가 잡는다.

4. **`npm run verify`** — 한 번. 여기서 이 시도는 끝난다.
   ```bash
   npm run verify    # 준비 → 타입 → 린트 → 아키텍처 → 테스트 → 빌드
   ```
   실패하면 **멈춘 단계를 적어 둔다.** 다음 시도가 거기서부터 본다.

5. **시도 코멘트를 즉시 단다** (§6). 통과든 실패든 예외 없다.
   **코멘트가 없는 시도는 다음 세션에 없던 일이 된다** (LOOP-5).

실패했고 시도가 남아 있으면 1~5를 다시 돈다. 상한을 다 쓰면 `중단(상한 소진)`으로 사람에게 넘긴다.

## 6. 시도 코멘트

```bash
gh issue comment <N> --body-file <파일>
```

양식은 03 §3 그대로다. AI가 채운다 — 사람은 양식을 외우지 않는다 (DEC-7).

```
### 시도 N/M · 통과 | 실패 | 중단(NEEDS_HUMAN) | 중단(상한 소진)
- 기준: <커밋 sha | uncommitted | PR #N · sha>
- verify: 로컬 통과 · CI 통과 | 실패(<멈춘 단계>) | 실행 안 함
- 한 일:
  - <파일 경로> — <무엇을 왜>
- 사람 판단이 필요한 것: 없음 | <내가 스스로 정한 것까지 전부>
- 다음 시도에서 할 것: 없음(종료) | <내용>
```

- `기준` — 커밋 전이면 `uncommitted`라고 솔직히 적는다. 같은 sha면 로컬과 CI가 한 시도다 (LOOP-11)
- `한 일` — **파일 단위로.** 다음 세션은 이 줄로 작업 트리를 읽는다
- `중단(NEEDS_HUMAN)`은 `verify` 칸을 `실행 안 함`으로 적는다. 돌리지 않았어도 시도 1회를 쓴 것이다 (LOOP-6)

## 7. 통과 후 — 커밋 · 푸시 · PR

로컬 verify가 통과한 뒤에만 연다. **실패한 코드를 CI로 확인하지 않는다** (03 §5).

커밋 메시지는 이 저장소의 방식대로 — 제목 `<type>: <한 일> (#N)`, 본문은 **왜**를 먼저 쓰고
파일별 요약, 마지막에 하지 않은 것 · 경계. 세션의 attribution 규칙이 있으면 그 줄을 끝에 붙인다.

```bash
git add -A && git commit
git push -u origin feat/issue-<N>-<기능명>
gh pr create --title "<제목>" --body "$(cat <<'EOF'
Closes #<N>

시도 기록은 그 Issue 코멘트에 있다.
EOF
)"
```

**PR 본문에 시도 이력을 옮기지 않는다** (LOOP-4). PR은 한 작업에 여럿 생길 수 있고 닫히면 흐름이 끊긴다.
PR 생성은 시도를 쓰지 않는다 (⊕0).

## 8. CI 폴링

같은 커밋이면 로컬 verify와 CI verify는 **한 시도**다 (LOOP-11).

```bash
gh pr checks --watch              # 끝날 때까지 지켜본다 (대기 중이면 exit 8)
```

| 결과 | 처리 | 카운트 |
|---|---|---|
| 통과 | §9 LLM 리뷰로 | ⊕0 |
| 실패 | **같은 커밋 그대로 re-run 1회** → `gh run rerun <run-id> --failed` | — |
| re-run 통과 | 환경 문제였다. 시도 코멘트 `verify` 칸에 `CI 통과(re-run)`이라고 보탠다 | ⊕0 |
| re-run 재실패 | 코드 문제로 본다. `복귀` 코멘트를 달고 §5로 돌아간다 | **⊕1** |
| 새 커밋 때문에 취소됨 | 실패가 아니다 (`cancel-in-progress`). 새 실행을 본다 | — |

원인을 주관으로 가르지 않는다 (LOOP-14). re-run 했다는 사실은 **코멘트에 적어야만 남는다.**

```
### 복귀 · PR #<번호>
- 사유: CI 실패(<단계>) · re-run도 실패
- 처리: ⊕1 → 시도 N+1/M
```

## 9. LLM 리뷰 — CI 통과 뒤의 자문

`verify`는 "코드가 도는가"를 보고 사람은 "요구한 대로 됐는가"를 본다. 그 사이를 메우는 자문이다.
**Issue 계약 심사이지 일반 코드 리뷰가 아니다** (DEC-10).

서브에이전트를 **깨끗한 맥락으로** 띄운다. 구현 대화를 넘기면 자기가 쓴 코드를 자기 기억으로 읽게 되어
자문이 되지 않는다. 프롬프트 전문은 `references/llm-review-prompt.md`에 있다 — 리뷰를 돌릴 때 읽는다.

결과는 PR 코멘트로 단다.

```bash
gh pr comment <PR번호> --body-file <파일>
```

```
## LLM 리뷰 · 시도 N/M · <sha>
- 종료 조건: C2 ✓ · C3 ✓ · C5 ⚠ 테스트가 불변식을 실제로 보지 않음 (tests/…:42)
- 보호 영역: 위반 없음
- 범위 밖 변경: <파일 · 무엇> — Issue에 없음
- 사람이 볼 것: C5
```

**합격 · 불합격을 쓰지 않는다.** 쓰는 순간 책임이 옮겨가고 `(수동)` 확인이 형식이 된다 —
완료 판정은 언제나 사람이다 (DEC-4). 리뷰는 힘이 없어서 실패하거나 아예 돌지 않아도 루프를 막지 않는다.
`gh` 코멘트는 사람 계정 이름으로 달리므로 **첫 줄에 `## LLM 리뷰`를 반드시 박는다.**

## 10. 사람 차례로 넘기고 멈춘다

```
### 사람 차례 · PR #<번호>
- 기준: <sha> · 시도 N/M 까지 씀
- 사람이 할 것:
  - (수동) 종료 조건 <C번호> — <어디서 무엇을 보면 되는지 구체적으로>
  - 리뷰 · CI 확인 후 merge · 승인 (DEC-4 완료 판정은 사람)
```

여기서 **끝난다.** merge도 승인도 하지 않는다 (DEC-5). 사람에게는 PR 링크와
`(수동)` 조건 확인 방법을 한 번에 알아볼 수 있게 요약해 준다.

사람이 말을 주면 그 말을 **네 갈래 중 하나로 분류**해 `사람 판단` 코멘트로 옮겨 적고 (04 §3),
그 갈래가 시키는 대로 한다.

| 갈래 | 판별 | 처리 |
|---|---|---|
| 승인 | 더 고칠 게 없다 | 루프 종료 · 지시 대기 |
| 반려 | **Issue 본문은 그대로인데** 결과가 못 미침 | ⊕1로 §5 복귀 |
| 판단 확정 | `NEEDS_HUMAN`에 대한 답. 본문은 그대로 | 시도 0/M 초기화 후 §5 |
| 요구사항 변경 | 사람이 **본문을 고쳤다고 알림** | 루프 닫힘 · 지시 대기 |

가르는 기준은 **Issue 본문**이다. 애매하면 분류하지 말고 되묻는다 (DEC-1 ①).
"다시 해봐" 같은 재시도 지시만으로는 초기화되지 않는다 — 전제가 그대로면 같은 상한 안에서 이어간다.

## 멈춰야 하는 순간 — NEEDS_HUMAN

어느 단계에서든 아래에 걸리면 추측으로 메우지 않고 멈춘다 (DEC-1).

1. 종료 조건의 해석이 갈린다
2. SSOT §0 충돌 정책에 걸린다 (Issue가 `REQ-*` · `ARCH-*` · 하네스 규칙과 충돌)
3. Issue 6개 항목이 비었거나 종료 조건을 참 · 거짓으로 판정할 수 없다
4. 보호 영역을 바꿔야 한다고 판단했다
5. 기록과 실제 상태가 어긋난다 (코멘트는 실패인데 트리는 통과 등)

부르기 전에 Issue와 SSOT에서 답이 나오는지 먼저 본다 (AGENTS.md 탐색 규칙: 1차 → 2차 → 3차, 한 칸씩).
멈출 때는 **어느 규칙과 어느 규칙이 충돌하는지** 적어서 넘긴다. 시도 1회를 쓰고 (LOOP-6),
`중단(NEEDS_HUMAN)` 코멘트를 남긴다.

## 절대 하지 않는 것

- **Issue 본문 수정** — 바꿔야 할 내용은 코멘트로 제안한다 (SSOT §0)
- **`docs/harness/` · SSOT §1 §2 · `docs/01-requirements.md` · `docs/06-architecture.md` 수정** — 읽기 전용
- **검증 스크립트 수정** — `scripts/check-architecture.ts` · `scripts/prepare-verify.ts` ·
  `package.json`의 verify 스크립트 · `.github/workflows/` 는 실행만 한다.
  verify를 통과시키려고 검사를 낮추면 관문 자체가 사라진다 (VER-3)
- **기존 테스트의 기대값 변경** — 바꿔야 하면 전제를 사람에게 검토받는다 (VER-4)
- **verify 실패를 "무시해도 되는 실패"로 판정** — 루프는 판정의 내용을 다시 따지지 않는다 (02 §2)
- **merge · 완료 선언 · 승인** — 사람 몫이다 (DEC-4 · DEC-5)
- **Issue 범위 밖의 개선** — 눈에 보여도 새 Issue로 제안만 한다

## 자주 쓰는 명령

```bash
gh issue view <N>                      # 계약 6개 항목
gh issue view <N> --comments           # 시도 횟수의 원본
gh issue comment <N> --body-file f.md  # 시도 · 복귀 · 사람 판단 기록
npm run verify                         # 한 시도의 끝
gh pr create / gh pr checks --watch    # 사람 구간 진입 · CI
gh run rerun <run-id> --failed         # CI 실패 시 딱 1회
gh pr comment <PR> --body-file f.md    # LLM 리뷰 보고서
```
