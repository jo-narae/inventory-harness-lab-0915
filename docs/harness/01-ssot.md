## 0. SSOT 규칙

1. **이 문서가 요구사항·아키텍처 규칙의 원본이다.** 원문은 상세 참고용이다.
2. 여기에는 **핵심 규칙만** 둔다. 배경·예시·세부 표는 원문을 본다.
3. 규칙을 바꿀 때는 **이 문서를 먼저 고치고, 코드는 그다음**에 고친다. 이 문서의 변경은 사람이 한다 (아래 보호 정책).
4. 원문에 근거가 없는 내용은 지어내지 않고 **미정**에 남긴다.
5. 사람의 판단이 필요한 경우 **`NEEDS_HUMAN`** 상태를 선언한다. 아래 충돌 정책·보호 정책에서 사람에게 넘기는 경우가 모두 여기에 해당한다.
6. **개별 작업의 원본은 그 작업의 GitHub Issue**다. 이 문서는 모든 작업에 공통인 규칙, Issue는 그 작업 하나의 범위와 완료 기준이다 (아래 Issue 절).

### Issue — 개별 작업의 SSOT

작업은 Issue 하나에서 시작하고 Issue 하나로 끝난다. 양식은 `.github/ISSUE_TEMPLATE/maintenance.yml`(유지보수 계약서 6개 항목)이다.

- 작업의 배경 · 변경할 내용 · 종료 조건 · 기계 검증 · 건드리면 안 되는 것 · 구현 루프 최대 횟수는 **Issue를 기준으로 판단**한다. 대화 · 계획 문서 · HANDOVER에 다른 내용이 있어도 그 작업에서는 Issue를 따른다
- Issue에 없는 변경은 하지 않는다. 필요하다고 판단하면 직접 넓히지 않고 새 Issue를 제안한다
- Issue는 이 문서의 규칙(§0~§3)을 넘어서지 못한다. 충돌하면 아래 충돌 정책대로 중단한다
- 6개 항목이 비어 있거나 종료 조건을 참 · 거짓으로 판정할 수 없으면 추측으로 채우지 않고 `NEEDS_HUMAN`을 선언한다
- Issue 본문은 사람이 고친다. AI는 바꿔야 할 내용을 Issue 코멘트로 제안한다
- 작업 완료는 ① 자동 검증 종료 조건이 `tests/issues/issue-{번호}-{기능명}.test.ts`에서 통과하고 ② `npm run verify`가 통과하고 ③ `(수동)` 종료 조건을 사람이 확인했을 때다

### 충돌 정책 — 사람에게 넘길 판단

| 충돌 | 판단 |
|---|---|
| 작업 요청(Issue)이 요구사항·아키텍처·하네스 규칙과 충돌 | **중단**하고 사람에게 확인한다 |
| 계획 문서(07-plan)·HANDOVER가 그 작업의 Issue와 다름 | 그 작업에서는 **Issue**를 따른다 |
| 참고 문서(01~06 원문, HANDOVER)가 SSOT와 다름 | **SSOT**를 따른다 |
| 계획 문서(07-plan 등)가 요구사항과 다름 | **요구사항**을 따른다 |
| SSOT 규칙끼리 충돌 (예: `REQ-*` ↔ `ARCH-*`) | 사람이 기준을 고치기 전까지 **구현하지 않는다** |

> **에이전트가 임의로 충돌을 해소하면 판단 기준 하나를 지우는 것이다.**
> 중단할 때는 어느 규칙과 어느 규칙이 충돌하는지 적어서 사람에게 넘긴다.

### 보호 정책 — 영역별 소유권

읽기 권한과 변경 권한을 영역별로 나눈다.

| 영역          | 대상                       | AI              | 사람       |
| ----------- | ------------------------ | --------------- | -------- |
| 작업 요청       | GitHub Issue 본문          | **읽기** · 코멘트로 제안 | 작성 · 변경  |
| 애플리케이션 코드   | `src/`                   | Issue 범위 안에서 수정 | 최종 승인    |
| Issue별 테스트  | `tests/` (Issue 종료 조건은 `tests/issues/`) | 작성 · 수정         | 전제 검토    |
| 요구사항 · 아키텍처 | 이 문서 §1·§2, 원문 01·06     | **읽기**          | 변경 · 승인  |
| 하네스 핵심 규칙   | 이 문서 §0, `docs/harness/` | **읽기**          | 변경 · 승인  |
| 검증 스크립트     | `npm run verify`         | 실행              | 정책 변경 승인 |

> AI가 읽기 전용 영역을 바꿔야 한다고 판단하면, 직접 고치지 않고 변경안을 제안해서 사람에게 넘긴다.

## 1. 요구사항

유통기한 단위(로트)로 여러 거점의 재고를 관리하고, 팝업 반출·정산까지 추적하는 사내 재고관리 앱.
**1차 목적은 강의·시연용 PoC(로컬 실행)**, 팀 내부 실사용은 향후 목표다.
상세 → [01-requirements.md](../01-requirements.md) (기능 F1~F11 · 사유 체계 F5-1 · 비기능 §5 · 범위 제외 §6)

**핵심 규칙**
- **REQ-1** 로트 = 상품 × 거점 × 유통기한. 재고는 사라지지 않고 거점 사이를 이동한다 (배송 중·폐기도 거점)
- **REQ-2** 출고는 **FEFO**(임박분 먼저), **풀필먼트 발송만 LEFO**(넉넉한 분 먼저)
- **REQ-3** 모든 증감에는 사유가 붙는다. 위치 이동에는 사유가 없다
- **REQ-4** 팝업 판매량은 `누적 반출 − 반입`으로 역산한다
- **REQ-5** 만료 재고는 자동으로 빠지지 않는다. 사람이 폐기를 확정한다
- **REQ-6** 이력은 수정·삭제할 수 없다. 되돌리기는 상쇄 기록으로만 한다
- **REQ-7** 재고가 음수가 되는 입력은 거부한다

**미정** — 백업·복구 절차, 성능 기준(1초) 측정 방법, 실사용 시 운영 환경

## 2. 아키텍처

Next.js 16 · Prisma 7 + SQLite · Server Actions (API 라우트·상태관리 라이브러리 없음).
상세 → [06-architecture.md](../06-architecture.md) (데이터 모델 §3 · 핵심 로직 §4 · 인증 §6 · 시드 §7)

**핵심 규칙**
- **ARCH-1** 재고 수량 변경은 `src/lib/stock.ts`의 `applyMovement()` **한 곳에서만** 한다
- **ARCH-2** 재고 변경과 이력 기록은 **같은 트랜잭션**에서 함께 성공하거나 함께 롤백된다
- **ARCH-3** `Movement`가 이력의 원본, `Lot.quantity`는 현재값이다
- **ARCH-4** 로트 배분은 `src/lib/fefo.ts`의 `planAllocation()` 하나로 화면과 서버가 같이 쓴다
- **ARCH-5** Prisma는 서버에서만 쓰고, 상태값은 `src/lib/constants.ts` 상수로 제한한다

**원문 정정** — 06 원문의 `middleware.ts`는 `src/proxy.ts`, `lib/format.ts`는 `src/lib/date.ts`, `tailwind.config.ts`는 `globals.css`의 `@theme`로 바뀌었다. 팝업 상태 `SETTLING`은 쓰지 않는다.

**미정** — 배포·서버 운영, 계정·비밀 관리, 취소 가능 기간과 권한

## 3. 검증

`npm run verify` — 준비 → 타입 → 린트 → 아키텍처 → 테스트 → 빌드.
이 절은 **판정만** 다룬다. 몇 번까지 다시 시도하고 언제 멈추는지는 §4 구현 루프가 맡는다.
상세 → [02-verification.md](02-verification.md) (파이프라인 §2 · 아키텍처 규칙 §3 · 알려진 빈틈 §4) · 원문: 완료 기준 01 §7 · 불변식 06 §9 · QA 체크리스트 [07-plan.md](../07-plan.md) §2

**핵심 규칙**
- **VER-1** 자동 검증 관문은 `npm run verify` 하나다. 로컬과 CI(PR · `main` push)가 같은 명령을 쓴다
- **VER-2** 매번 검증 전용 `prisma/verify.db`를 새로 시드해서 시작한다. `dev.db` 상태에 결과가 좌우되지 않는다
- **VER-3** 한 단계라도 실패하면 멈춘다. 검증 스크립트를 고쳐서 통과시키지 않는다 — 스크립트 변경은 사람이 승인한다 (§0 보호 정책)
- **VER-4** 테스트 기대값을 바꿔야 하면 그 전제를 사람에게 검토받는다 (§0 보호 정책)
- **VER-5** verify 통과는 완료가 아니다. 완료는 01 §7을 실제 데이터로 확인했을 때다

**미정** — DB 검증 단계, 검증 스크립트의 보호 범위, CI 체크의 PR 병합 필수 지정 (상세 → 02 §5)

## 4. 구현 루프

**검증(§3)은 변경이 옳은지 판정하고, 루프는 그 판정을 받아 계속할지 멈출지 정한다.**
`npm run verify`는 시도 횟수를 모르고, 루프는 verify의 내부 단계를 모른다.

규칙의 원본은 [03-loop.md](03-loop.md)다 (핵심 규칙 `LOOP-*` §1 · 시도 기록 양식 §3 · 세션 복구 §4 · PR과 CI §5).
시도 횟수의 원본은 **그 작업 Issue의 코멘트**다 — 세션 컨텍스트 · 대화 · 작업 트리는 원본이 아니다.
