# 04. 사람의 개입 — 누가 무엇을 결정하는가

> 작성일: 2026-09-16 · 기준 커밋: `d70c046`
> 사람이 개입해야 하는 지점과 그 결정을 받는 절차의 원본은 이 문서다. [SSOT](01-ssot.md) §5는 루프와의 경계만 선언한다.
> **소유권**(누가 무엇을 바꿀 수 있나)의 원본은 SSOT §0 충돌 정책 · 보호 정책이다. 이 문서는 그 소유권을 **어떻게 주고받는가**를 정한다.
> 이 문서의 변경은 사람이 한다 (SSOT §0 보호 정책).

---

## 1. 핵심 규칙

**넘기는 법 — AI가 멈춰야 하는 지점**

- **DEC-1** 다음 중 하나에 걸리면 추측으로 메우지 않고 멈춰 **`NEEDS_HUMAN`**을 선언한다 — ① 종료 조건의 해석이 갈림 ② SSOT §0 충돌 정책에 걸림 ③ Issue 6개 항목이 비었거나 종료 조건을 참 · 거짓으로 판정할 수 없음 ④ 보호 영역(SSOT §0)을 바꿔야 한다고 판단함 ⑤ 기록과 실제 상태가 어긋남. 사람을 부르기 전에 Issue와 SSOT에서 답이 나오는지 먼저 본다 (AGENTS.md 탐색 규칙)
- **DEC-2** 보호 영역은 직접 고치지 않고 **변경안을 제안**한다. Issue 본문은 코멘트로, 문서 · 검증 스크립트는 사람의 승인을 받아서 바꾼다 (SSOT §0 보호 정책 · VER-3 · VER-4)
- **DEC-3** 멈추지 않고 AI가 스스로 정한 판단도 시도 코멘트의 `사람 판단이 필요한 것` 칸에 전부 적는다. 적지 않으면 그 판단은 검토되지 않은 채 굳는다
- **DEC-4** **완료 판정은 사람이 한다.** 루프가 끝난 것은 완료가 아니다. 완료는 ① 자동 검증 종료 조건이 `tests/issues/issue-{번호}-{기능명}.test.ts`에서 통과하고 ② `npm run verify`가 통과하고 ③ `(수동)` 종료 조건을 사람이 확인했을 때다 (SSOT §0 Issue 절)
- **DEC-5** **merge · 승인은 사람이 한다.** AI는 PR 생성까지만 한다. merge 없이 PR을 닫으면 사람이 중단한 것으로 본다 — AI는 스스로 재개하지 않는다

**받는 법 — 사람의 결정이 들어오는 경로**

- **DEC-6** 사람의 승인 · 반려 · 판단은 **자연어로 AI에게 말하면 된다.** 정해진 장소도 문법도 없다. AI가 그 말을 받아 §3 「사람 판단」 코멘트로 옮겨 적는다
- **DEC-7** **양식은 AI가 채우는 것이다.** 사람은 양식을 찾거나 외우지 않는다. 이 문서와 [03-loop.md](03-loop.md)의 코멘트 양식은 전부 AI의 몫이다
- **DEC-8** 사람이 **Issue 본문을 고치면 그 사실을 한 줄 알린다** — 형식은 자유다. AI에게 말해도 되고 Issue에 아무 양식 없이 남겨도 된다. AI는 본문만 보고 스스로 분류하지 않는다 (§4 알려진 빈틈)

**가르는 법 — 네 갈래**

- **DEC-9** 사람의 결정은 아래 넷 중 하나로 분류해서 적는다. 이 네 이름이 루프에 건네는 유일한 신호다 (§2)

| 갈래 | 무엇인가 | 판별 |
|---|---|---|
| **승인** | 구현을 받아들인다 | 더 고칠 것이 없다고 말함 |
| **반려** | **요구사항대로 구현되지 않았다** — AI의 미구현 | Issue 본문은 그대로인데 결과가 그에 못 미침 |
| **판단 확정** | 갈리던 해석을 사람이 정해 줬다 | `NEEDS_HUMAN`에 대한 답. **Issue 본문은 그대로** |
| **요구사항 변경** | Issue 본문의 요구사항 · 종료 조건 · 범위가 바뀌었다 | 사람이 본문을 고쳤다고 알림 (DEC-8) |

> **반려와 요구사항 변경을 가르는 기준은 Issue 본문이다.** 지적이 본문에 이미 있는 것을 못 지켰다는 뜻이면 반려,
> 본문 자체를 바꾸는 뜻이면 요구사항 변경이다. 애매하면 분류하지 않고 사람에게 되묻는다 (DEC-1 ①).

**자문을 받는 법**

- **DEC-10** PR을 열었다면 CI `verify`가 통과한 뒤, 사람이 승인 · 반려를 판단하기 전에 **LLM 리뷰**를 돌리고 결과를 PR 코멘트로 남긴다 (§3). 리뷰는 판정이 아니라 **자문**이므로 루프를 막지 않고 합격 · 불합격을 쓰지 않는다. 사람이 그 보고서를 보고 반려하면 그때부터 루프의 몫이다

## 2. 루프와의 책임 분리

|          | 사람의 개입 (이 문서)                     | 루프 ([03-loop.md](03-loop.md))        |
| -------- | ----------------------------------- | ------------------------------------ |
| 무엇을 정하는가 | 누가 결정하는가 · 그 결정이 무엇인가               | 그 결정이 시도 횟수에 무엇을 하는가                 |
| 수단       | `NEEDS_HUMAN` 선언 · 네 갈래 분류 · 코멘트 기록 | Issue §6 상한 · ⊕0 · ⊕1 · 초기화           |
| 모르는 것    | 몇 번째 시도인지 · 상한이 얼마인지                | 사람이 한 말이 무슨 뜻인지                       |

**이 문서는 사람의 말을 네 이름 중 하나로 바꾸고, 루프는 그 이름만 보고 센다.**
두 문서를 잇는 계약은 이 표가 전부다.

| 이 문서의 갈래 | 루프에 주는 효과 | 근거 |
|---|---|---|
| 승인 | 루프 종료 · 지시 대기 | LOOP-12 |
| 반려 | ⊕1 복귀 | LOOP-13 |
| 판단 확정 | 시도 0으로 **초기화** | LOOP-7 |
| 요구사항 변경 | 루프 **닫힘** | LOOP-8 |
| `NEEDS_HUMAN` 중단 | **⊕1** — 멈추는 것은 공짜가 아니다 | LOOP-6 |

> 루프가 사람의 말을 다시 해석하면 갈래가 둘이 되고, 이 문서가 시도를 세면 상한이 둘이 된다.

## 3. 기록

사람의 결정도 **Issue 코멘트**에 남는다. 세션 밖에 남는 유일한 상태이기 때문이다 (LOOP-4).
AI는 Issue 본문을 고치지 않는다 — 기록도 제안도 코멘트로 한다 (SSOT §0 보호 정책).

### 사람 판단 코멘트

사람이 자연어로 말한 것을 AI가 받아 적는다 (DEC-6 · DEC-7).
사람이 Issue 본문을 고쳤다고 알려온 것도 여기로 들어온다 (DEC-8).

```
### 사람 판단 · 승인 | 반려 | 요구사항 변경 | 판단 확정
- 받은 말: <사람이 말한 것>
- 어디서: 대화 | PR #N 리뷰 | Issue 코멘트
- 처리: 승인         → 루프 종료 · 지시 대기 (merge · 완료 선언은 사람)
        반려         → ⊕1 시도 N+1/M 로 재구현
        요구사항 변경  → 종료(LOOP-8) · 지시 대기
        판단 확정     → 초기화 시도 0/M 후 재구현 (LOOP-7)
- 다음에 할 것: 없음(대기) | <내용>
```

`판단 확정`으로 적은 코멘트 **뒤부터** 시도를 1회차로 다시 센다.

> 초기화는 **사람이 판단을 내렸을 때만** 일어난다. 재시도 지시("다시 해봐")만으로는 초기화되지 않는다 —
> 전제가 그대로면 같은 상한 안에서 이어가는 것이 맞다.

`NEEDS_HUMAN`으로 멈춘 것은 시도 코멘트로 적는다 — 양식은 [03-loop.md](03-loop.md) §3이다.

### LLM 리뷰 — CI 통과 뒤의 자문

`verify`는 "코드가 도는가"를 보고, 사람은 "요구한 대로 됐는가"를 본다. 그 사이가 비어 있다.
LLM 리뷰는 그 빈자리를 메우는 자문이다 — **Issue 계약 심사**이지 일반 코드 리뷰가 아니다.

| | 내용 |
|---|---|
| 언제 | CI `verify`가 통과한 뒤에만. 실패한 코드를 심사할 이유가 없다 |
| 누가 | **PR을 올린 세션.** GitHub Actions job이 아니다 — 워크플로 수정도 API 키 시크릿도 필요 없다 |
| 입력 | Issue 본문(종료 조건 C1~Cn · §5 보호 영역) · PR diff · 그 Issue의 시도 기록 · SSOT §0 · `REQ-*` · `ARCH-*`. **구현 대화 맥락은 주지 않는다** — 자기가 쓴 코드를 자기 기억으로 읽으면 자문이 되지 않는다 |
| 보는 것 | ① 종료 조건 ↔ 구현 · 테스트 대조 (통과하지만 실제로는 검증하지 않는 테스트 포함) ② 보호 영역 침범 · Issue에 없는 범위 밖 변경 |
| 안 보는 것 | `verify`가 이미 보는 것 — 타입 · 린트 · 아키텍처 B1~B6 · 테스트 통과 · 빌드 |
| 출력 | **PR 코멘트.** 합격 · 불합격을 쓰지 않고 관찰만 적는다 |
| 힘 | 없다. 리뷰가 실패하거나 아예 돌지 않아도 루프를 막지 않는다 (카운트는 03 §5) |

```
## LLM 리뷰 · 시도 N/M · <sha>
- 종료 조건: C2 ✓ · C3 ✓ · C5 ⚠ 테스트가 불변식을 실제로 보지 않음 (tests/…:42)
- 보호 영역: 위반 없음
- 범위 밖 변경: src/lib/popup.ts createPopupTx 추출 — Issue에 없음
- 사람이 볼 것: C5
```

세션에서 도는 순서는 이렇다.

```
gh pr create …                     # PR을 연다 (로컬 verify 통과 후 — LOOP-10)
gh pr checks --watch               # CI가 끝날 때까지 지켜본다 (대기 중이면 exit 8)
  → bucket 이 pass 일 때만 다음으로
서브에이전트에 위 입력만 주고 리뷰   # 구현 대화 맥락은 넘기지 않는다
gh pr comment --body-file …        # 보고서를 PR에 단다
```

`gh`로 다는 코멘트는 **사람의 GitHub 계정 이름으로 달린다.** 그래서 본문 첫 줄에 `## LLM 리뷰`를
반드시 박아 사람이 직접 쓴 말과 구분한다. Actions bot이 달아주는 것이 아니다.

**보고서는 PR에, 그 보고서로 내린 결정은 Issue에** 남는다. 리뷰는 기록이 아니라 그 순간의 판단
자료이므로 PR이 닫혀 묻혀도 루프를 복구하는 데 지장이 없다. 사람의 승인 · 반려만 Issue 코멘트로
남으면 된다 (DEC-9 · LOOP-4).

`합격`을 적지 않는 이유는 책임이 옮겨가지 않게 하기 위해서다. "LLM이 통과시켰으니 됐다"가 되면
`(수동)` 종료 조건 확인이 형식이 된다. 완료 판정은 언제나 사람이 한다 (DEC-4).
처음에는 위의 두 가지만 보게 한다 — 매번 여러 건을 외치면 사람이 읽지 않게 되고, 그러면 자문이
아니라 소음이 된다.

## 4. 알려진 빈틈

- Issue 본문 수정을 AI가 직접 관측할 수 없다 (`updatedAt` 시각만 보이고 무엇이 바뀌었는지는 모른다). 사람이 알리지 않으면(DEC-8) 바뀐 줄 모르고 옛 전제로 계속 돈다
- 초기화의 근거(`사람이 판단을 내렸는가`)를 기계가 가릴 수 없다. 코멘트를 남기는 쪽의 자기 신고에 기댄다
- 세션 밖에서 벌어진 사람의 행위(merge · close · 리뷰)는 AI가 코멘트로 옮겨 적지 않는 한 기록에 남지 않는다
- 반려와 요구사항 변경의 경계가 사람의 말투에 달려 있다. 사람이 본문을 고치고도 "이대로 다시 해줘"라고만 하면 AI는 반려로 읽는다
- LLM 리뷰는 같은 diff에도 다른 말을 할 수 있다. 재현되지 않으므로 관문으로 쓰지 않는다
- LLM 리뷰가 세션에 묶여 있다. 세션이 끊기거나 PR에 새 커밋이 올라와도 다시 돌지 않는다 — 사람이 PR만 열어봤을 때 보고서가 없거나 옛 커밋 기준일 수 있다
- 리뷰 코멘트가 사람 계정으로 달려, 제목을 놓치면 사람이 쓴 말과 섞인다
- PR 없이 진행하면 LLM 리뷰가 돌지 않는다. 종료 조건 대조를 사람 혼자 한다 (그래도 된다고 정했다 — DEC-10)

## 5. 미정

- `NEEDS_HUMAN`을 선언하기 전에 AI가 얼마나 찾아봐야 하는지의 기준 (AGENTS.md 탐색 규칙은 문서 범위만 정한다)
- 승인 뒤 사람이 아무 말 없이 멈췄을 때의 처리 (AI가 다시 물어도 되는지)
- 사람이 여러 명일 때의 결정 권한 (지금은 한 명 전제)
