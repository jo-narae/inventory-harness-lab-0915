# 03. 구현 루프 — 몇 번까지 시도하고 언제 멈추는가

> 작성일: 2026-09-16 · 기준 커밋: `f8ab1e5`
> 루프 규칙의 원본은 이 문서다. [SSOT](01-ssot.md) §4는 검증과의 경계만 선언한다.
> 이 문서의 변경은 사람이 한다 (SSOT §0 보호 정책). 시도 횟수의 원본은 **그 작업 Issue의 코멘트**다.

---

## 1. 핵심 규칙

**세는 법**

- **LOOP-1** 시도 1회 = 구현부터 `npm run verify` **실행까지**다. verify를 한 번 돌리면 결과와 무관하게 그 시도는 끝난다. verify 이전의 수정(린트 · 타입 오류 정정 포함)은 전부 같은 시도 안이다
- **LOOP-2** 시도가 끝나는 방식은 셋뿐이다 — ① `verify` 실행(통과 · 실패) ② `NEEDS_HUMAN` 중단(LOOP-6) ③ 사람 구간에서의 복귀(LOOP-13 · LOOP-14). 셋 중 무엇도 아닌 채로 끝난 작업은 시도로 세지 않고, 완료도 아니다
- **LOOP-3** 시도 상한은 그 작업 Issue의 §6이다. 상한을 다 쓰고도 종료 조건을 채우지 못하면 멈추고 `NEEDS_HUMAN`을 선언한다. 상한을 넘겨 계속하지 않는다
- **LOOP-4** 시도 횟수의 **원본은 Issue 코멘트**다. 세션 컨텍스트 · 대화 · 작업 트리 · PR은 원본이 아니다. 세션이 끊기면 다음 세션은 Issue 코멘트의 마지막 시도 번호부터 이어간다. 코멘트가 없으면 0회로 본다
- **LOOP-5** 시도가 끝날 때마다 통과 · 실패와 무관하게 Issue 코멘트를 남긴다 (§3 양식). 코멘트가 없는 시도는 다음 세션에 없는 것과 같다

**멈추고 다시 세는 법**

- **LOOP-6** 종료 조건의 해석이 갈리거나 SSOT §0 충돌 정책에 걸리면 추측으로 메우지 말고 멈추고 `NEEDS_HUMAN`을 선언한다. **이 중단은 실패와 똑같이 시도 1회를 쓴다** — `verify`를 돌리지 않았어도 센다. 멈추는 것은 공짜가 아니다. 사람을 부르기 전에 Issue와 SSOT에서 답이 나오는지 먼저 본다 (AGENTS.md 탐색 규칙)
- **LOOP-7** (초기화) **Issue 본문이 그대로인 채** 사람이 판단만 확정해 다시 지시하면 시도 횟수는 0으로 초기화된다. 상한도 처음부터 다시 센다. 기준이 명확해졌으므로 그 전의 시도는 다른 전제 위에서 돈 것이다
- **LOOP-8** (종료) 사람이 **Issue 본문의 요구사항 · 종료 조건 · 범위를 바꾸면** 이 루프는 그 자리에서 끝난다. 남은 시도와 상한은 의미를 잃고, 시도 기록은 종료 시점까지로 닫는다. 그 뒤의 처리 — Issue를 클로징할지, 새로 지시할지 — 는 루프 밖이며 사람이 정한다. AI는 스스로 재개하지 않는다
- **LOOP-9** 루프의 끝은 완료가 아니다. 완료 판정은 SSOT §0 Issue 절의 세 가지(① 자동 검증 종료 조건 ② `npm run verify` ③ `(수동)` 조건)를 사람이 확인했을 때다

**사람에게 넘기고 돌아오는 법**

- **LOOP-10** (턴 넘김) 로컬 `verify`가 통과하면 턴을 사람에게 넘기고 기록을 남긴다. 넘기는 것 자체는 시도를 쓰지 않는다(⊕0). **PR은 필수가 아니다** — 사람 구간을 굴리는 수단일 뿐이다. PR을 연다면 로컬 `verify`가 통과한 뒤에 열고, 본문에는 `Closes #<번호>`와 "시도 기록은 그 Issue 코멘트"만 적는다 (상세 → §5)
- **LOOP-11** 같은 커밋에 대한 로컬 `verify`와 CI `verify`는 **한 시도**다. 시도는 실행 횟수가 아니라 **판정받은 코드 상태**를 센다
- **LOOP-12** (대기) 사람 구간에 머무는 동안 시도는 소모되지 않는다. 마지막 기록이 「사람 차례」면 다음 세션은 사람 차례로 보고 새 시도를 시작하지 않는다
- **LOOP-13** (복귀) 리뷰가 "요구사항대로 구현되지 않았다"고 지적한 것은 **AI의 미구현**이다. ⊕1로 기계 구간에 복귀해 다시 구현한다. 지적이 요구사항 자체를 바꾸는 것이면 LOOP-8이다
- **LOOP-14** (CI 실패) 같은 커밋 그대로 **re-run을 한 번** 해본다. re-run이 통과하면 환경 문제였으므로 시도를 쓰지 않고(⊕0), 또 실패하면 코드 문제로 보고 ⊕1로 복귀한다. 원인을 주관으로 가르지 않는다. 새 커밋 때문에 이전 실행이 취소된 것(`cancel-in-progress`)은 실패가 아니다
- **LOOP-15** (출구) merge · 승인은 사람이 한다. AI는 PR 생성까지만 한다. **merge 없이 PR을 닫으면 사람이 중단한 것**으로 본다 — 시도 횟수는 그대로 남고, AI는 스스로 재개하지 않는다

**사람의 판단을 받는 법**

- **LOOP-16** 사람의 승인 · 반려 · 판단은 **자연어로 AI에게 말하면 된다.** AI가 그 말을 받아 §3 「사람 판단」 코멘트로 남기고, 갈래에 따라 처리한다 — 반려 · 판단 확정이면 기계 구간으로 들어가 다시 구현하고, 승인 · 요구사항 변경이면 코멘트만 남기고 지시를 기다린다. merge와 완료 선언은 사람이 한다 (LOOP-15 · LOOP-9)
- **LOOP-17** 이 문서의 코멘트 양식은 **AI가 채우는 것이다.** 사람은 양식을 찾거나 외우지 않는다
- **LOOP-18** 사람이 **Issue 본문을 고치면 그 사실을 한 줄 알린다** — 형식은 자유다. AI에게 말해도 되고 Issue에 아무 양식 없이 남겨도 된다. AI는 그 알림으로 초기화(LOOP-7)와 종료(LOOP-8)를 가르고 코멘트를 남긴다. 본문만 보고 스스로 분류하지 않는다

**CI 통과 뒤의 자문**

- **LOOP-19** PR을 열었다면 CI `verify`가 통과한 뒤, 사람이 승인 · 반려를 판단하기 전에 **LLM 리뷰**를 돌리고 결과를 **PR 코멘트**로 남긴다 (상세 → §5). PR을 올린 **그 세션이 이어서 한다** — CI를 지켜보다 통과하면 리뷰를 돌리고 코멘트를 달기까지가 한 흐름이다. 리뷰는 판정이 아니라 자문이므로 **시도를 쓰지 않고(⊕0) 루프를 막지 않는다.** 사람이 그 보고서를 보고 반려하면 그때 LOOP-13대로 ⊕1이다. PR 없이 사람 차례로 넘긴 작업에는 리뷰가 없다

## 2. 검증과 루프의 책임 분리

|          | 검증 ([02-verification.md](02-verification.md)) | 루프 (이 문서)                              |
| -------- | --------------------------------------------- | -------------------------------------- |
| 무엇을 보는가 | 변경한 코드                                        | 작업의 진행                                 |
| 수단       | `npm run verify` 한 줄                          | Issue §6 상한 · Issue 코멘트                |
| 결과       | 통과 · 실패                                       | 계속 · 중단(`NEEDS_HUMAN`) · 종료 · 완료로 넘김   |
| 상태의 위치   | `verify.db` — 매번 버리고 새로 만든다                   | Issue 코멘트 — 세션을 넘어 남는다                 |
| 모르는 것    | 몇 번째 시도인지 · 지금 누구 차례인지                        | verify가 어느 단계에서 무엇을 검사하는지              |

**검증은 판정만 하고 멈출지는 정하지 않는다. 루프는 판정의 내용을 다시 따지지 않는다.**
verify가 실패했는데 루프가 "이 실패는 무시해도 된다"고 판단하면 검증 관문이 사라진다 (VER-3).
반대로 루프의 상한을 verify 스크립트에 넣으면, 검증이 세션 상태를 알아야 해서 VER-2가 깨진다.

루프는 **기계 구간**(AI가 구현하고 verify가 판정)과 **사람 구간**(리뷰 · `(수동)` 종료 조건 · CI 재확인)이
턴을 주고받는 구조다. 사람 구간에서는 시도가 소모되지 않는다 (LOOP-12).

## 3. 시도 기록 — Issue 코멘트

세션 밖에 남는 유일한 상태다. 시도가 끝나거나 턴이 바뀔 때마다 하나씩 이어서 단다.
AI는 Issue 본문을 고치지 않는다 — 기록도 제안도 코멘트로 한다 (SSOT §0 보호 정책).

### 시도 코멘트

```
### 시도 N/M · 통과 | 실패 | 중단(NEEDS_HUMAN)
- 기준: <커밋 sha | uncommitted | PR #N · sha>
- verify: 로컬 통과 · CI 통과 | 실패(<멈춘 단계>) | 실행 안 함
- 한 일:
- 사람 판단이 필요한 것: 없음 | <목록>
- 다음 시도에서 할 것: 없음(종료) | <내용>
```

| 칸 | 왜 필요한가 |
|---|---|
| `시도 N/M` | 다음 세션이 몇 회차부터 이어갈지 정하는 값 (LOOP-4) |
| `기준` | 그 시도가 어느 코드 위에서 돌았는지. 커밋하지 않았으면 `uncommitted`라고 적어 작업 트리에만 있음을 알린다. 같은 sha면 로컬과 CI가 한 시도다 (LOOP-11) |
| `verify` | 멈춘 단계까지 적는다 — 다음 시도가 같은 단계부터 본다 |
| `한 일` | 파일 단위로 적는다. 다음 세션은 이 줄로 작업 트리를 읽는다 |
| `사람 판단이 필요한 것` | LOOP-6으로 멈추지 않고 내가 정한 것도 전부 적는다. 적지 않으면 그 판단은 검토되지 않은 채 굳는다 |
| `다음 시도에서 할 것` | 비어 있으면 루프가 끝났다는 뜻. 남은 수동 조건은 여기에 적는다 |

`NEEDS_HUMAN`으로 멈춘 시도도 같은 양식으로 적는다. 상태를 `중단(NEEDS_HUMAN)`으로 쓰고
`verify` 칸에는 `실행 안 함`이라고 적는다 — 돌리지 않았어도 시도 1회를 쓴 것이다 (LOOP-6).

### 턴 넘김 · 복귀 코멘트

```
### 사람 차례 · <PR #N | PR 없음>
- 기준: <sha> · 시도 N/M 까지 씀
- 사람이 할 것: 리뷰 | (수동) 종료 조건 <C번호> | merge · 승인

### 복귀 · <PR #N | PR 없음>
- 사유: 요구사항대로 안 됨 | CI 실패(<단계>) · re-run도 실패
- 처리: ⊕1 → 시도 N+1/M
```

CI가 실패했다가 **re-run으로 통과**했으면 복귀가 아니다. 시도 코멘트의 `verify` 칸에
`CI 통과(re-run)`이라고 적어 둔다 — 시도는 늘지 않는다 (LOOP-14).

### 사람 판단 코멘트

사람이 자연어로 말한 승인 · 반려 · 판단을 AI가 받아 적는다 (LOOP-16 · LOOP-17).
사람이 Issue 본문을 고쳤다고 알려온 것도 여기로 들어온다 (LOOP-18).

```
### 사람 판단 · 승인 | 반려 | 요구사항 변경 | 판단 확정
- 받은 말: <사람이 말한 것>
- 어디서: 대화 | PR #N 리뷰 | Issue 코멘트
- 처리: 승인         → 루프 종료 · 지시 대기 (merge · 완료 선언은 사람)
        반려         → ⊕1 시도 N+1/M 로 재구현
        요구사항 변경  → 종료(LOOP-8) · 지시 대기
        판단 확정     → 초기화 시도 0/M 후 재구현 (LOOP-7)
- 다음에 할 것: 없음(대기) | <내용>
```

`판단 확정`으로 적은 코멘트 **뒤부터** 시도를 1회차로 다시 센다.

> 초기화는 **사람이 판단을 내렸을 때만** 일어난다. 재시도 지시("다시 해봐")만으로는 초기화되지 않는다 —
> 전제가 그대로면 같은 상한 안에서 이어가는 것이 맞다.

### 멈춤 · 끝 표기

| 상태 | 언제 | 턴 |
|---|---|---|
| `중단(NEEDS_HUMAN)` | 해석이 갈리거나 §0 충돌 (LOOP-6) | 사람 |
| `중단(상한 소진)` | 남은 시도 0 (LOOP-3) | 사람 |
| `중단(사람이 PR 닫음)` | merge 없이 PR을 닫음 (LOOP-15) | 사람 |
| `종료(요구사항 변경)` | 사람이 Issue 본문을 바꿈 (LOOP-8) | 사람 — **루프는 닫혔다** |

## 4. 세션 복구 절차

작업을 이어받을 때 이 순서로 읽는다.

1. **Issue 본문** — 종료 조건 · 건드리면 안 되는 것 · §6 상한 (개별 작업의 SSOT)
2. **Issue 코멘트** — 뒤에서부터 읽는다. 마지막 코멘트가 **턴**을 정하고, `### 초기화` 코멘트가 있으면 **그 뒤의 시도만** 센다. 코멘트가 하나도 없으면 0회
3. **턴이 사람이면 손대지 않는다.** 아래 표로 판정한다
4. **`기준` 줄** — 커밋이면 그 sha, `uncommitted`면 작업 트리의 diff, `PR #N`이면 그 PR을 읽는다
5. **남은 시도 = M − N.** 0이면 새로 시도하지 않고 `NEEDS_HUMAN`으로 사람에게 넘긴다
6. 이어서 하기 전에 `npm run verify`를 **먼저 돌리지 않는다** — 그 자체로 한 번을 쓴다 (LOOP-1). 코드를 고친 뒤 마지막에 돌린다

| 마지막 코멘트 | 턴 | 다음 행동 |
|---|---|---|
| `시도 N/M · 실패` | AI | 남은 시도 확인 후 구현 |
| `시도 N/M · 통과` | AI | 턴을 사람에게 넘긴다 (원하면 PR) |
| `사람 차례` | **사람** | 손대지 않고 기다린다 |
| `복귀` | AI | 구현 |
| `사람 판단 · 반려` | AI | ⊕1로 구현 |
| `사람 판단 · 판단 확정` | AI | 초기화 — 1회차로 구현 |
| `사람 판단 · 승인` | **사람** | 루프는 끝났다. merge · 완료 선언을 기다린다 |
| `사람 판단 · 요구사항 변경` | **사람** | 루프는 닫혔다. 지시를 기다린다 |
| `중단(…)` 세 가지 | **사람** | 판단을 기다린다 |
| `종료(요구사항 변경)` | **사람** | 루프는 닫혔다. 지시를 기다린다 |
| 없음 | AI | N=0부터 시작 |

> 코멘트와 작업 트리가 다르면 (예: 코멘트는 `시도 2/3 · 실패`인데 트리는 통과하는 상태)
> 판단하지 않고 사람에게 확인한다 — 기록되지 않은 시도가 있었다는 뜻이다 (SSOT §0 충돌 정책).
> 이 확인 자체는 `NEEDS_HUMAN` 중단이므로 시도 1회를 쓴다 (LOOP-6).

## 5. PR과 CI

**PR은 필수가 아니다.** 사람 구간을 굴리는 수단이고, 리뷰나 CI 재확인이 필요 없으면 PR 없이
`사람 차례` 코멘트만으로 넘긴다. 이 문서는 PR을 쓸 때의 규칙만 정한다.
(`main` 직접 push 정책과 CI 체크의 병합 필수 지정은 [02-verification.md](02-verification.md) §5의 미정 항목이다.)

| 시점 | 무엇을 하는가 | 카운트 |
|---|---|---|
| **진입** | 로컬 `verify` 통과 후에만 PR을 연다. 실패한 코드를 CI로 확인하지 않는다 | ⊕0 |
| PR 본문 | `Closes #<번호>` + "시도 기록은 그 Issue 코멘트" 한 줄. 기록을 PR로 옮기지 않는다 | — |
| **CI** | `.github/workflows/verify.yml`이 로컬과 같은 `npm run verify`를 돌린다 (VER-1) | 같은 커밋이면 ⊕0 (LOOP-11) |
| CI 실패 | 같은 커밋 그대로 **re-run 1회** → 통과면 환경 문제 | ⊕0 |
| CI 재실패 | 코드 문제로 본다 → 기계 구간 복귀 | **⊕1** |
| 리뷰 지적 | 요구사항대로 안 된 것 → 복귀 / 요구사항을 바꾸는 것 → LOOP-8 종료 | **⊕1** / — |
| **LLM 리뷰** | PR을 올린 세션이 CI `verify` 통과를 확인한 뒤 돌린다. 결과는 PR 코멘트 (아래) | ⊕0 |
| **출구** | merge · 승인은 사람. merge 없이 닫으면 `중단(사람이 PR 닫음)` | ⊕0 |

### LLM 리뷰 — CI 통과 뒤의 자문

`verify`는 "코드가 도는가"를 보고, 사람은 "요구한 대로 됐는가"를 본다. 그 사이가 비어 있다.
LLM 리뷰는 그 빈자리를 메우는 **자문**이다 — **Issue 계약 심사**이지 일반 코드 리뷰가 아니다.

| | 내용 |
|---|---|
| 언제 | CI `verify`가 통과한 뒤에만. 실패한 코드를 심사할 이유가 없다 |
| 누가 | **PR을 올린 세션.** GitHub Actions job이 아니다 — 워크플로 수정도 API 키 시크릿도 필요 없다 |
| 입력 | Issue 본문(종료 조건 C1~Cn · §5 보호 영역) · PR diff · 그 Issue의 시도 기록 · SSOT §0 · `REQ-*` · `ARCH-*`. **구현 대화 맥락은 주지 않는다** — 자기가 쓴 코드를 자기 기억으로 읽으면 자문이 되지 않는다 |
| 보는 것 | ① 종료 조건 ↔ 구현 · 테스트 대조 (통과하지만 실제로는 검증하지 않는 테스트 포함) ② 보호 영역 침범 · Issue에 없는 범위 밖 변경 |
| 안 보는 것 | `verify`가 이미 보는 것 — 타입 · 린트 · 아키텍처 B1~B6 · 테스트 통과 · 빌드 |
| 출력 | **PR 코멘트.** 합격 · 불합격을 쓰지 않고 관찰만 적는다 |
| 힘 | 없다. ⊕0이고, 리뷰가 실패하거나 아예 돌지 않아도 루프를 막지 않는다 |

```
## LLM 리뷰 · 시도 N/M · <sha>
- 종료 조건: C2 ✓ · C3 ✓ · C5 ⚠ 테스트가 불변식을 실제로 보지 않음 (tests/…:42)
- 보호 영역: 위반 없음
- 범위 밖 변경: src/lib/popup.ts createPopupTx 추출 — Issue에 없음
- 사람이 볼 것: C5
```

세션에서 도는 순서는 이렇다.

```
gh pr create …                     # PR을 연다 (로컬 verify 통과 후 — LOOP-10)
gh pr checks --watch               # CI가 끝날 때까지 지켜본다 (대기 중이면 exit 8)
  → bucket 이 pass 일 때만 다음으로
서브에이전트에 위 입력만 주고 리뷰   # 구현 대화 맥락은 넘기지 않는다
gh pr comment --body-file …        # 보고서를 PR에 단다
```

`gh`로 다는 코멘트는 **사람의 GitHub 계정 이름으로 달린다.** 그래서 본문 첫 줄에 `## LLM 리뷰`를
반드시 박아 사람이 직접 쓴 말과 구분한다. Actions bot이 달아주는 것이 아니다.

**보고서는 PR에, 그 보고서로 내린 결정은 Issue에** 남는다. 리뷰는 기록이 아니라 그 순간의 판단
자료이므로 PR이 닫혀 묻혀도 루프를 복구하는 데 지장이 없다. 사람의 승인 · 반려만 Issue 코멘트로
남으면 된다 (LOOP-4 · LOOP-16).

`합격`을 적지 않는 이유는 책임이 옮겨가지 않게 하기 위해서다. "LLM이 통과시켰으니 됐다"가 되면
`(수동)` 종료 조건 확인이 형식이 된다. 완료 판정은 언제나 사람이 한다 (LOOP-9).
처음에는 위의 두 가지만 보게 한다 — 매번 여러 건을 외치면 사람이 읽지 않게 되고, 그러면 자문이
아니라 소음이 된다.

CI가 로컬과 다른 결과를 낼 수 있는 지점은 워크플로에 적힌 것들이다 — `ubuntu-latest` 러너,
Node 22, `npm ci`, `TZ=Asia/Seoul`, CI 전용 `DATABASE_URL` · `SESSION_SECRET`, `timeout-minutes: 15`.
**기록의 원본은 언제나 Issue 코멘트 하나다** (LOOP-4). PR은 한 작업에 여러 개 생길 수 있고
닫히면 흐름이 끊기므로, 시도 이력을 PR 코멘트에 두지 않는다.

## 6. 알려진 빈틈

- 코멘트 작성이 사람 · AI의 손에 달려 있다. 빠뜨리면 그 시도는 없던 것이 된다 — 자동화 수단이 없다
- 한 Issue를 여러 세션이 동시에 잡으면 시도 번호가 겹친다. 동시 작업을 막는 장치가 없다
- 초기화의 근거(`사람이 판단을 내렸는가`)를 기계가 가릴 수 없다. `### 초기화` 코멘트를 남기는 쪽의 자기 신고에 기댄다
- PR 없이 진행하면 CI도 LLM 리뷰도 돌지 않는다. 그 작업의 검증은 로컬 `verify` 한 번뿐이라 환경 차이가 드러나지 않고, 종료 조건 대조도 사람 혼자 한다 (그래도 된다고 정했다 — LOOP-19)
- LLM 리뷰는 같은 diff에도 다른 말을 할 수 있다. 재현되지 않으므로 관문으로 쓰지 않는다
- LLM 리뷰가 세션에 묶여 있다. 세션이 끊기거나 PR에 새 커밋이 올라와도 다시 돌지 않는다 — 사람이 PR만 열어봤을 때 보고서가 없거나 옛 커밋 기준일 수 있다
- 리뷰 코멘트가 사람 계정으로 달려, 제목을 놓치면 사람이 쓴 말과 섞인다
- re-run을 했는지는 코멘트에 적어야만 남는다. GitHub의 실행 이력과 어긋나도 알 수 없다
- Issue 본문 수정을 AI가 직접 관측할 수 없다 (`updatedAt` 시각만 보이고 무엇이 바뀌었는지는 모른다). 사람이 알리지 않으면(LOOP-18) 바뀐 줄 모르고 옛 전제로 계속 돈다
- 세션 밖에서 벌어진 사람의 행위(merge · close · 리뷰)는 AI가 코멘트로 옮겨 적지 않는 한 기록에 남지 않는다

## 7. 미정

- 실패한 시도의 코드를 되돌리는지 (다음 시도가 이어서 고치는지, 깨끗한 상태에서 다시 시작하는지)
- 초기화가 여러 번 이어질 때의 상한 (같은 Issue에서 무한히 초기화되는 것을 막을지)
- `main` 직접 push 정책 · CI 체크를 병합 필수로 지정할지 → [02-verification.md](02-verification.md) §5
- 코멘트 작성 자동화 (`gh issue comment` 래핑 스크립트 · CI에서의 자동 기록)
